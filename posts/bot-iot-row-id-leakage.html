The row ID that scored 100%: data leakage in the Bot-IoT dataset

I rebuilt an old IoT botnet-detection project and, before training anything, tested each column on its own. One of them, the dataset's row ID, separated attacks from normal traffic perfectly. Here's how that happens, why many reported scores on this dataset deserve suspicion, and what an honest evaluation looks like.

The dataset

Bot-IoT was recorded in a UNSW Canberra cyber range: simulated IoT devices, normal traffic and botnet attacks. I used the authors' 5% extract with their "10-best features" and official train/test split: 2,934,817 training rows and 733,705 test rows.

Trap one: accuracy

The test set contains 107 normal flows out of 733,705. A "model" that answers attack for everything scores 99.985% accuracy while recognising none of them. Any result on this dataset quoted as accuracy alone tells you almost nothing, so I compared models on balanced accuracy, macro F1, and two numbers a security team actually cares about: the false-positive rate (normal traffic flagged as an attack) and the attack detection rate.

Trap two: leakage

Before training a real model, I ran a simple screen: train a tiny decision tree on one column at a time and measure balanced accuracy, where 0.5 is a coin flip. A column that predicts the label almost perfectly on its own is either the most informative feature in the world or something that shouldn't be a feature at all.

for col in columns:
    x = encode(sample[col]).reshape(-1, 1)
    tree = DecisionTreeClassifier(max_depth=3, class_weight="balanced")
    tree.fit(x_train, y_train)
    score = balanced_accuracy_score(y_test, tree.predict(x_test))

A row number carries no information about network behaviour. It scores perfectly because of how the dataset was assembled: normal and attack records were captured and numbered in separate blocks, so the ID encodes the label. IP addresses and ports behave similarly. They identify the lab's victim machines and attack setup, which a model memorises and which won't exist on any other network.

Measuring the inflation

To put numbers on it, I retrained the best model (Random Forest) four ways and evaluated each on the same untouched test set:

ExperimentBalanced acc.Macro F1False positivesRelied on most
A. Behavioural features only0.9790.9571.87%srate
B. + identifier columns1.0000.9920.00%pkSeqID
C. Row ID only1.0000.9990.00%pkSeqID
D. No whole-capture counts0.8620.76421.50%srate

Experiment C is the finding: a model that knows nothing about network traffic beats every honest model. When a paper reports near-perfect results on Bot-IoT without saying which columns were removed, it may be measuring the dataset's numbering, not attack detection.

Experiment D is the uncomfortable follow-up. The two connection-count features are counted over the entire capture. They're real behavioural signals (floods produce huge connection counts), but a detector running live wouldn't have whole-capture totals up front. Without them, the false-positive rate jumps from 1.87% to 21.5%. A deployable version would need those counts computed over a sliding time window.

The honest results

With identifiers removed, training-only rebalancing (cap the huge classes, oversample the rare ones; the test set is never touched) and five models on 14 behavioural features:

Two details are worth pointing out. Random Forest's plain accuracy (99.62%) is lower than the always-attack baseline, yet it's by far the better detector. And the LSTM's recall looks fine class by class, but it labels about 0.23% of attacks as normal. That's roughly 1,670 attacks hiding in a "normal" bucket that genuinely holds only 107 flows, which is why its macro F1 is 0.52. The deep sequence model was slower and worse than a Random Forest on tabular flow features.

A checklist I'll reuse

  1. Report per-class metrics, never accuracy alone, whenever classes are imbalanced.
  2. Run a single-feature screen before modelling. Anything near-perfect on its own needs an explanation.
  3. Ask whether each feature exists at detection time. Whole-dataset aggregates often don't.
  4. Rebalance training data only; evaluate on the real class mix.
  5. Be honest about sample size. My 1.87% false-positive rate is 2 of 107 flows; one more error moves it by about a point.
